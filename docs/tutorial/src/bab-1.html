Dunia 2.5D dan EnemySwarm

Bab paling penting. Di sini fondasi seluruh game dipasang: dunia 3D yang dilihat dari kamera miring, sprite pixel yang berdiri menghadap kamera, dan cara menggerakkan serta menggambar ribuan musuh tanpa membuat ribuan node.

TujuanPemain berjalan di padang rumput tak berujung. Musuh muncul makin banyak dari luar layar, mengejar, saling menjauh supaya tidak bertumpuk, dan didorong oleh Holy Aura yang memberi damage tiap 0,6 detik. Tekan F1: 500 musuh tambahan, game tetap mulus.

Konsep: Node, Scene, dan Resource

Konsep · Godot

Node adalah satuan terkecil di Godot: sesuatu yang punya nama, posisi di pohon, dan (opsional) skrip. Scene adalah pohon node yang disimpan ke file .tscn dan bisa dipakai berulang (di-instance), seperti player.tscn yang dimasukkan ke main.tscn. Resource adalah data tanpa posisi di pohon: tekstur, mesh, material, atau kelas data milikmu sendiri seperti EnemyData. Resource disimpan sebagai .tres dan dibagi oleh siapa pun yang memuatnya.

Aturan praktis di proyek ini: sesuatu yang perlu ada di dunia dan jumlahnya sedikit (pemain, kamera, HUD) = node. Sesuatu yang jumlahnya ribuan (musuh, proyektil, gem) = baris data di array, digambar oleh satu node. Sesuatu yang mendeskripsikan (statistik ghoul, statistik senjata) = Resource.

Knellbound terlihat 3D, tapi semua logika berjalan di bidang datar. Posisi pemain adalah pos2: Vector2; komponen x = sumbu X dunia, komponen y = sumbu Z dunia. Node 3D hanya menyalin nilai itu untuk digambar:

Keuntungannya besar: jarak, tabrakan, dan arah semua memakai Vector2 (dua angka, bukan tiga), tidak perlu fisika 3D, dan tidak pernah ada musuh yang "jatuh" atau tersangkut di lantai. Ketinggian (proyektil melayang, vial yang dilempar melengkung) hanya ditambahkan saat menulis buffer gambar.

Langkah 1: scene main.tscn

  1. Scene → New Scene, pilih 3D Scene. Rename root jadi Main. Simpan sebagai scenes/main.tscn. Di Project Settings → Application → Run → Main Scene pilih file ini (Fase 7 menggantinya dengan title).
  2. Tambah child WorldEnvironment. Di Inspector buat New Environment: Background Mode Custom Color gelap, Ambient Light dari warna, Tonemap Filmic, aktifkan Glow. Glow penting nanti: warna di atas 1,0 (aura, proyektil, outline elite) akan berpendar.
  3. Tambah DirectionalLight3D bernama Sun. Sprite memakai shader unshaded, jadi lampu hanya memengaruhi tanah.
  4. Tambah MeshInstance3D bernama Ground, Mesh = PlaneMesh 160×160. Material: StandardMaterial3D, Albedo Texture = art/tiles/grass.png, UV1 Triplanar + World Triplanar aktif, UV1 scale 0,125, Texture Filter Nearest.

Trik tanah tak berujung: plane 160×160 digeser mengikuti pemain tiap frame (ground.position = Vector3(player.pos2.x, 0, player.pos2.y) di Game._process). Karena UV-nya world triplanar, tekstur dihitung dari posisi dunia, bukan dari posisi mesh. Mesh bergerak, rumputnya diam. Pemain tidak pernah melihat tepi.

Langkah 2: kamera orthographic miring

Konsep · Camera3DPerspective membuat benda jauh tampak kecil. Orthographic tidak: semua benda tampak sebesar ukuran aslinya, berapa pun jaraknya, seperti gambar teknik. Untuk pixel art, ortho berarti satu piksel sprite selalu menjadi jumlah piksel layar yang sama di seluruh layar. Properti size pada kamera ortho = tinggi area yang terlihat, dalam unit dunia.

Buat node Node3D bernama CameraRig, beri child Camera3D, lalu tempel skrip core/camera_rig.gd. Rig berada di tanah mengikuti pemain; kameranya duduk di ujung "lengan" yang miring.

  • 28Dengan pitch p dan jarak 30, kamera berada sin(p)·30 di atas dan cos(p)·30 di belakang rig. Itu trigonometri biasa: sisi segitiga siku-siku dengan sudut p.
  • 29Lalu kamera diputar menunduk sebesar -p di sumbu X, sehingga ia menatap tepat ke rig.
  • 33ortho_size = 13: layar memperlihatkan 13 unit dunia secara vertikal. Karena 16 piksel = 1 unit dan layar 720 piksel, satu piksel art jadi kira-kira 3 piksel layar.

Baris 44 adalah pola yang akan sering kamu lihat: lerp dengan faktor 1 - exp(-k·dt). Kalau kamu menulis lerp(target, 0.2) tiap frame, kamera mengikuti lebih cepat di 144 FPS daripada di 60 FPS. Dengan eksponen, hasilnya sama berapa pun FPS-nya: setelah 1 detik selalu tersisa exp(-12) dari jarak awal. Knockback musuh (Fase 1) dan peluruhan shake (Fase 6) memakai ide yang sama.

  5. Child Node3D Weapons: senjata akan ditambahkan sebagai anak node ini saat run.

billboard = 2 adalah BILLBOARD_FIXED_Y: sprite hanya berputar di sumbu Y menghadap kamera, tetap tegak lurus tanah. Billboard penuh (1) akan ikut menunduk 50° dan terlihat rebah.

Inilah alasan angka 1.55 muncul di mana-mana (y_stretch di setiap Field, scale Y Sprite3D pemain). Sprite berdiri tegak, kamera menunduk 50°, jadi tinggi sprite di layar menyusut menjadi cos 50° ≈ 0,643. Dikali 1,55 hasilnya ≈ 1,0: piksel art tetap persegi. Tanah sendiri menyusut sin 50° ≈ 0,766, yang memberi kesan perspektif miring. Itulah "2.5D".

Konsep: kenapa musuh bukan node

Konsep · data-oriented design

Cara paling mudah membuat musuh adalah scene enemy.tscn dengan skrip yang punya _process sendiri, lalu di-instance 1000 kali. Untuk 50 musuh itu baik-baik saja. Untuk 1000+ ada tiga biaya yang menumpuk:

  • Panggilan per node. Tiap frame Godot memanggil 1000 _process, masing-masing lewat mesin skrip. Biaya panggilan itu sendiri sudah signifikan di GDScript.
  • Transform per node. Mengubah position node memicu notifikasi transform, update ke RenderingServer, dan pengecekan AABB, satu per musuh.
  • Memori tersebar. Data tiap musuh ada di objek berbeda di memori. CPU paling cepat membaca data yang berurutan.

Solusinya: simpan semua musuh sebagai baris di beberapa array yang paralel: pos[i], hp[i], speed[i], … semuanya milik musuh ke-i. Satu loop memproses semuanya. Untuk menggambar, satu MultiMesh menerima satu buffer berisi transform semua musuh sekaligus.

Packed array (PackedVector2Array, PackedFloat32Array, PackedInt32Array) menyimpan angka berjejer rapat tanpa pembungkus Variant, jauh lebih hemat dan cepat dibanding Array biasa.

Konsep · copy-on-write

Packed array di GDScript adalah nilai dengan copy-on-write: var b := pos tidak menyalin datanya, tapi begitu kamu menulis ke b, Godot menyalin seluruh array agar pos tidak ikut berubah. Dua akibat yang terlihat di kode:

  • Di _ready, tiap array di-resize langsung lewat namanya (bukan lewat loop atas daftar array), karena alias lokal akan meresize salinan.
  • Di upload(), penulisan ke _buf dan _large_buf sengaja ditulis dua kali dalam dua cabang alih-alih var b := _large_buf if … else _buf, karena alias itu akan menyalin buffer tiap frame.

Membaca lewat alias aman dan murah. Itu sebabnya _separate() boleh menulis var starts := _grid.cell_start: hanya dibaca.

Statistik musuh tidak ditulis di kode. Buat kelas Resource:

  1. Simpan skrip di enemies/enemy_data.gd. Karena ada class_name EnemyData, kelas ini terdaftar global.
  2. Di FileSystem klik kanan data/enemies/ → Create New → Resource…, cari EnemyData, simpan sebagai ghoul.tres.
  3. Klik file itu: semua @export muncul di Inspector. Isi Max HP 12, Move Speed 2,2, Contact Damage 8.

File .tres adalah teks. Kamu bisa membacanya, men-diff-nya, dan menyeimbangkan game tanpa membuka kode. Di Fase 5 EnemyData berkembang (perilaku, tembakan), tapi prinsipnya sama: nilai disalin ke array swarm saat spawn, sehingga loop panas tidak pernah membaca Resource.

Langkah 5: EnemySwarm.spawn dan hapus swap-with-last

Buat Node3D EnemySwarm di main.tscn, tempel enemies/enemy_swarm.gd, isi sheet dengan art/sprites/enemies.png. Slot 0..count-1 hidup. Spawn = tulis ke slot count, lalu count += 1.

Menghapus musuh di tengah array dengan remove_at akan menggeser semua elemen di belakangnya: O(n), dan dikali ratusan kematian per detik. Karena urutan musuh tidak berarti apa-apa, cukup salin elemen terakhir ke lubang:

Dua hal halus di flush_dead: kematian dikumpulkan dulu di _dead dan diproses setelah semua senjata selesai (supaya indeks tidak berubah di tengah loop senjata), lalu _dead diurutkan dan diproses dari belakang. Kalau slot 3 dan 9 mati dan 9 adalah slot terakhir, menghapus 3 dulu akan memindahkan isi slot 9 ke 3, lalu "hapus 9" menghapus musuh yang salah.

Langkah 6: menggambar dengan MultiMesh

Konsep · MultiMesh dan RenderingServer

MultiMesh menggambar satu mesh sebanyak N kali dalam satu draw call, masing-masing dengan transform dan data warnanya sendiri. RenderingServer adalah API tingkat rendah tempat node visual Godot sebenarnya berbicara. Dengan RenderingServer.multimesh_set_buffer(rid, buffer) kita mengirim semua data instance dalam satu panggilan, bukan N panggilan set_instance_transform.

  • 169TRANSFORM_3D + use_custom_data: tiap instance = 12 float transform + 4 float custom = 16 float (STRIDE).
  • 172instance_count diset sekali ke kapasitas penuh. Yang berubah tiap frame hanya visible_instance_count; mengubah instance_count akan mengalokasikan ulang buffer GPU.
  • 175custom_aabb raksasa: Godot tidak perlu menghitung ulang kotak pembatas dari ribuan instance, dan MultiMesh tidak pernah ter-cull karena AABB lama.

Setiap musuh menulis 16 float. Dari 12 float transform, hanya 5 yang berubah: skala di diagonal (indeks 0, 5, 10) dan posisi x, z (indeks 3, 11). Sisanya tetap 0, jadi tidak perlu ditulis ulang. Empat float terakhir menjadi INSTANCE_CUSTOM di shader.

Bayangan memakai buffer yang sama (_shadow_mm diberi _buf juga): transformnya identik, dan shader bayangan mengabaikan data custom. Dua MultiMesh, dua panggilan, nol kerja tambahan di CPU.

Shader sprite billboard

MultiMesh tidak punya opsi billboard seperti Sprite3D, jadi shader sprite_billboard.gdshader melakukannya sendiri, sekaligus memilih frame animasi, membalik sprite, dan memberi hit flash dari INSTANCE_CUSTOM.

  • vertexframe = floor(mod(TIME * fps + INSTANCE_CUSTOM.x, hframes)): animasi berjalan di GPU. CPU tidak perlu mengirim frame tiap saat; phase acak per musuh membuat gerombolan tidak bergerak serempak.
  • uvKalau INSTANCE_CUSTOM.y < 0, uv.x = 1 - uv.x: sprite dicerminkan, menghadap kiri.
  • VERTEX.yDikali y_stretch sebelum rotasi.
  • MODELVIEWMatriks dibangun ulang: sumbu X = arah kanan kamera diproyeksikan ke horizontal, sumbu Y = tegak dunia, sumbu Z = cross keduanya, posisi = posisi instance. Lalu dikali skala instance (panjang kolom MODEL_MATRIX). Hasilnya: billboard sumbu Y untuk setiap instance.
  • fragmentALPHA_SCISSOR_THRESHOLD = 0.5: piksel transparan dibuang, sisanya opak. Sprite bisa ditulis ke depth buffer sehingga urutan depan-belakang benar tanpa sorting.

Langkah 7: gerak musuh

Satu loop untuk semua musuh. Versi Fase 1 hanya punya satu perilaku: kejar pemain.

  • seekv = d * (speed / |d|): vektor ke pemain dinormalisasi lalu dikali kecepatan. Satu akar kuadrat per musuh. Ini perilaku seek paling dasar.
  • relokasiMusuh yang tertinggal lebih dari 34 unit dipindah ke cincin 20 unit di sisi seberang, yaitu ke arah pemain sedang berjalan. Pemain yang lari terus tidak meninggalkan ribuan musuh tak berguna di belakang.
  • knockKnockback disimpan terpisah dari kecepatan kejar, ditambahkan ke gerak, lalu meluruh knock *= exp(-knock_decay·dt).
  • gridSetelah semua bergerak, grid dibangun ulang dan separasi dijalankan.

Langkah 8: SpatialHash

Separasi, damage aura, proyektil, dan tabrakan dengan pemain semuanya bertanya hal yang sama: musuh mana yang dekat titik ini? Mengecek semua musuh berarti O(n) per pertanyaan; separasi (setiap musuh bertanya) menjadi O(n²): 1000 musuh = sejuta cek per frame.

Konsep · uniform grid + hash

Bagi dunia menjadi sel persegi (1,2 unit). Musuh hanya perlu dicek terhadap musuh di sel yang sama dan sel tetangga. Karena dunia tidak terbatas, koordinat sel (cx, cy) di-hash ke tabel berukuran tetap 4096 bucket: ((cx · 73856093) ^ (cy · 19349663)) & 4095. Dua sel jauh bisa jatuh ke bucket yang sama (tabrakan hash), jadi pemanggil tetap harus mengecek jarak sebenarnya.

Grid dibangun ulang dari nol setiap frame karena semua musuh bergerak. Supaya murah, build() memakai counting sort: tidak ada Array per sel, tidak ada alokasi, hanya tiga loop di atas packed array yang dipakai ulang.

Query lingkaran mengunjungi semua sel yang disentuh kotak pembatas lingkaran (diperbesar dengan radius musuh terbesar), lalu mengecek jarak. Satu musuh bisa ditemukan dua kali kalau dua sel berbagi bucket; _stamp mencegah itu tanpa perlu membersihkan apa pun: setiap query punya nomor baru, dan musuh yang sudah dicap nomor itu dilewati.

Separasi yang murah

Tiga trik membuat separasi muat dalam anggaran frame:

  1. Hanya blok 2×2 sel terdekat. Karena sel (1,2) ≥ 2× radius musuh, semua tetangga yang mungkin bertumpuk pasti ada di 2×2 sel di sekitar titik, bukan 3×3. Sel kedua dipilih dari sisi mana titik berada di dalam selnya (fx - cx >= 0.5).
  2. Maksimal 12 tetangga. Di tengah gerombolan padat, mengecek 12 sudah cukup untuk dorongan yang meyakinkan.
  3. Bergiliran (stagger). separation_stride = 2: frame ganjil memproses musuh ganjil, frame genap yang genap. Separasi adalah efek visual yang lembut; setengah frekuensi tidak terlihat bedanya, biayanya setengah.

Dorongan dibatasi limit_length(0.3) per frame supaya musuh tidak "meledak" keluar saat banyak yang bertumpuk sekaligus.

Langkah 9: senjata pertama, Holy Aura

Senjata adalah node anak Player/Weapons, jadi otomatis ikut bergerak bersama pemain. Kelas dasar Weapon di Fase 1 nyaris kosong:

Statistiknya di WeaponData (Resource), perilakunya di scene + skrip turunan Weapon. Scene weapons/aura/aura_weapon.tscn: root Node3D dengan skrip aura, child Visual (MeshInstance3D, PlaneMesh 2×2 rebah, material_override = ShaderMaterial dengan shaders/aura.gdshader).

Damage tidak dicek tiap frame. Aura menunggu timer, lalu satu query_circle mengambil semua musuh di radius. Setiap hit melewati satu fungsi, damage_enemy, yang mengurangi HP, menyalakan hit flash, dan menambah knockback. Semua senjata yang datang kemudian memakai jalur yang sama.

Shader aura menggambar cakram dengan tepi berkuantisasi piksel (pixel_steps = radius × 2 × 16, jadi resolusi cakram cocok dengan 16 px per unit), cincin rune berputar, dan riak. blend_add + warna di atas 1 membuat glow WorldEnvironment menangkapnya.

Langkah 10: SpawnDirector sederhana

Fase 1 memakai laju spawn yang naik linear terhadap waktu. Laju dihitung dalam spawn per detik dan dikumpulkan di akumulator: setiap frame _acc += laju · dt, dan selama akumulator ≥ 1 kita spawn satu cluster lalu menguranginya. Dengan cara ini 2,5 spawn/detik benar-benar menghasilkan 2,5 per detik, berapa pun FPS-nya.

Musuh muncul berkelompok (3–7) di cincin radius 20, sedikit di luar layar (layar setinggi 13 unit). Fase 5 mengganti ini dengan tabel wave berbasis data.

Langkah 11: Game memegang urutan

Terakhir, tempel core/game.gd di root Main. Inilah versi Fase 1 lengkap: perhatikan bahwa tidak ada sistem lain yang punya _process.

Konsep · kenapa satu pemilik urutan

Kalau tiap node punya _process, urutan pemanggilannya ditentukan posisi di pohon scene. Memindahkan satu node di editor bisa membuat senjata membaca posisi musuh frame lalu, atau gem jatuh di posisi yang sudah diganti slot lain. Dengan satu daftar di Game._process, urutannya terbaca dari atas ke bawah, bisa diuji, dan perubahan disengaja. Bonus: pause cukup satu baris (if get_tree().paused: return), dan hit-stop di Fase 6 cukup melewati semua kecuali kamera.

dt dibatasi 1/20 detik. Kalau game tersendat (misalnya jendela diseret), satu frame panjang tidak membuat musuh melompat menembus pemain.

Dekorasi tak berujung

DecorField menggambar rumput, batu, jamur, dan nisan dengan teknik yang sama (MultiMesh + shader billboard), tapi hanya menulis ulang buffer saat pemain pindah petak 40×40. Satu petak acak diulang 3×3 di sekitar pemain.

Checkpoint
  • Tekan F5. Pemain berjalan dengan WASD, kamera mengikuti dengan halus, rumput tidak pernah habis.
  • Musuh muncul dari luar layar, mengejar, tidak menumpuk jadi satu titik, berkedip putih saat kena aura, dan terdorong keluar.
  • Label debug menunjukkan FPS dan jumlah musuh. F1 menambah 500 musuh. Di Fase 1 game ini tetap di atas 60 FPS dengan lebih dari 1000 musuh di PC desktop biasa.
Kesalahan umum & cara debug
  • Musuh tidak terlihat sama sekali. Cek urutan: instance_count sudah diisi sebelum multimesh_set_buffer? visible_instance_count diisi n? Ukuran buffer harus persis instance_count × 16; kalau tidak, Godot mencetak error di Output.
  • Semua musuh menumpuk di titik (0,0) atau gepeng. Indeks buffer salah. Posisi ada di indeks 3 dan 11, skala di 0, 5, 10. Pakai demo buffer di atas untuk mengecek.
  • Musuh hilang saat kamera bergerak jauh. Lupa custom_aabb: Godot meng-cull MultiMesh berdasarkan AABB lama.
  • Sprite terlihat pendek/gepeng. y_stretch atau scale Y Sprite3D tidak 1,55.
  • FPS jatuh di 300 musuh. Biasanya ada pembacaan Resource atau alokasi di loop panas (mis. Array baru per musuh). Buka Debugger → Profiler, jalankan, lihat fungsi dengan Self time terbesar.
